# Dashboard exchange-rate layer

Status: implementation specification grounded in the 13 uploaded entity files. No application code or database has been changed. The provider, Currency enum, DbContext, dependency-injection setup, project files, and reporting services were not supplied, so a working integration and build cannot yet be verified.

## 1. Agreed requirement and proposed defaults

Fetch one complete set of exchange rates for the whole application every 24 hours, save it in the database, and reuse it for every client and report. The stated provider allowance is 1,500 requests per month; this has not yet been verified against a named provider.

One request per day is possible only if the selected plan returns all required currencies in one response and charges that response as one request. Its fixed base currency is sufficient: cross rates can be calculated locally.

Proposed reporting policy: use the latest saved rate snapshot for all amounts in a requested report, including amounts from earlier dates. Preserve previous snapshots, but do not imply that today's rates are historical transaction-date rates. Historical conversion requires a separate policy and potentially a historical-data endpoint. Under the proposed policy, an old report's converted totals can change when exchange rates change; exports should retain the snapshot ID and rate timestamp.

## 2. Fit with the supplied entities

| Existing field | Proposed meaning and treatment |
| --- | --- |
| `Client.Currency` | Currency used to display client-wide totals and monetary targets. |
| `Platform.Currency` | Source currency of that advertising account's metrics. |
| `Campaign.Currency` | Already exists alongside platform currency. Validate that it agrees with its platform under the account-currency policy; do not silently convert using an inconsistent field. |
| `AdDailyMetrics.Spend`, `Revenue` | Preserve original source-currency amounts in storage. Convert when building reporting totals. |
| `SearchTerm.Spend` | Same source currency as its account, reached through AdSet → Campaign → Platform. Search-term data is a separate breakdown and must not be added to ad-metric spend again. |
| `ClientTarget` monetary fields | Interpret in the client's reporting currency; changing that currency needs explicit handling of existing targets. |

These monetary fields currently use `double`. Use `decimal` for exchange rates and conversion calculations. A coordinated migration of Spend, Revenue, SearchTerm.Spend, and monetary target/DTO fields to `decimal` is recommended; changing C# types alone is insufficient and cannot recover precision already lost. Monetary precision and scale must be chosen from actual supported value ranges. Microsoft's [numeric-type guidance](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/floating-point-numeric-types) explains the distinction.

No relationship to users, Identity tables, individual clients, campaigns, or ads is needed for the shared rates.

## 3. Proposed database additions

| Table | Essential fields | Purpose |
| --- | --- | --- |
| `ExchangeRateSnapshot` | `Id`, `Provider`, `BaseCurrencyCode`, `RatesAsOfUtc`, `FetchedAtUtc` | One complete validated response. The provider's effective timestamp and our fetch timestamp remain distinct. |
| `ExchangeRate` | `SnapshotId`, `QuoteCurrencyCode`, `Rate` (`decimal`) | Units of quote currency per one base-currency unit. Composite primary key: `(SnapshotId, QuoteCurrencyCode)`. Include the base currency with rate 1. |
| `ExchangeRateSyncState` | `QuotaScope`, `LatestSnapshotId`, `LastAttemptUtc`, `LastSuccessUtc`, `NextAttemptUtc`, `BudgetPeriodStartUtc`, `BudgetPeriodEndUtc`, `ReservedRequests`, `AttemptDayUtc`, `AttemptsToday`, `LeaseToken`, `LeaseExpiresUtc`, concurrency token | Persistent scheduling, publication pointer, request limits, and coordination across restarts and server instances. One row per provider subscription/quota scope. |

`QuotaScope` is a nonsecret identifier. It must remain stable across API-key rotation and represent the actual shared subscription limit. Keep API keys in server configuration/secrets, not in these rows.

Use explicit ISO currency-code mapping after inspecting the existing Currency enum. Do not assume enum numeric values or names match the provider. Validate positive rates and required currency coverage. A possible rate precision is `decimal(28,12)`, subject to the provider's documented ranges.

Insert a snapshot and all of its rates, then update `LatestSnapshotId`, in one transaction. Readers resolve one snapshot ID per report and use it throughout. Never expose a partial rate set or combine two snapshots. EF Core's [transaction support](https://learn.microsoft.com/en-us/ef/core/saving/transactions) supplies the database mechanism.

## 4. Responsibilities

| Component | Responsibility |
| --- | --- |
| `IExchangeRateProvider` / provider adapter | Make one HTTP request and normalize the actual provider response. The endpoint, authentication, schema, timestamps, and error codes depend on its documentation. |
| `ExchangeRateSyncService` | Decide whether a fetch is due; reserve quota and claim work; validate and publish a response; schedule bounded retries. |
| `ExchangeRateRepository` | Read snapshots and perform atomic state/lease/budget updates. |
| `ExchangeRateWorker` | Check on startup and periodically thereafter; call the sync service. A check that is not due makes no external request. |
| `CurrencyConversionService` | Convert using a supplied saved snapshot; never call the provider. |
| Existing aggregation services | Sum native values by source currency, convert monetary subtotals, and recalculate derived KPIs. |

Use a typed HttpClient for the adapter and a BackgroundService for the worker. Resolve scoped services/DbContext inside a fresh scope for each worker iteration, as described in Microsoft's [hosted-service documentation](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/host/hosted-services?view=aspnetcore-10.0). A five-minute scheduling check is sufficient; these are DB checks, not five-minute provider calls.

## 5. Refresh and quota rules

1. On startup, check saved state. Fetch immediately only when missing or due. A restart does not bypass `NextAttemptUtc` or reset request counts.
2. Before sending, atomically verify that work is due, the lease is free, the daily cap is available, and the current billing-period budget is below 1,500. Claim a bounded lease, reserve one request, and persist the attempt timestamp and recovery schedule. Commit before calling the provider.
3. Only the winning claimant may send the request. Use a database concurrency mechanism, not just an in-memory lock. Keep database transactions short; the HTTP call happens outside the transaction. Lease ownership must be checked when publishing so an expired claimant cannot overwrite newer data. The HTTP timeout must be shorter than the lease.
4. Count every outbound attempt conservatively, including retries, timeouts, failed responses, and ambiguous outcomes. A crash after reservation may overcount by one, which is safer than exceeding the allowance. Do not automatically refund reservations.
5. On valid success, atomically publish the complete snapshot and schedule the next normal fetch 24 hours later. Use provider publication/next-update information to refine scheduling once documented. An unchanged provider timestamp is not evidence of newly published rates.
6. On transient failure, keep the last usable snapshot. Allow at most two retries, proposed after 15 minutes and then 60 minutes. All trigger paths share an additional cap of three outbound requests per UTC day. Persist retry timing and attempt counts so restarts cannot cause loops.
7. Honor a later `Retry-After` time and all provider limits. Pause on invalid credentials/configuration until corrected. If the subscription quota is exhausted, wait for its documented reset. After the daily allowance is exhausted, defer to the next eligible day.
8. Disable uncounted HTTP retry/hedging middleware and automatic redirects that could generate additional billable requests. Every additional network attempt must go through the same budget reservation path.
9. A manual refresh, if added later, must use the same freshness, concurrency, and budget gates. Opening pages, switching tabs, changing date ranges, and refreshing advertising data do not themselves fetch exchange rates.

| Activity | External-request budget |
| --- | --- |
| Normal operation | About 28–31 requests per calendar month. |
| Three attempts every day, including retries | At most 93 in a 31-day period under the proposed daily cap. |
| All clients, reporting conversions, tab changes | Zero additional requests. |
| Hard guard | Never reserve a request that would take this integration over its configured allowance of at most 1,500 in the provider's billing period. |

Configure the actual billing reset date/time; do not assume the first day of the calendar month. If the subscription/key is used elsewhere, its existing and external usage must be included or a smaller dedicated allocation must be assigned. A local counter alone cannot guarantee a subscription-wide limit when other consumers are invisible.

## 6. Conversion and aggregation

All rates in a snapshot share the same base. For an amount in currency A converted to currency B:

```csharp
converted = amount * rates[B] / rates[A];
```

Illustrative values only: if one USD equals 3.75 SAR and 50 EGP, 100 SAR equals `100 * 50 / 3.75`, approximately 1,333.33 EGP. No second provider request is needed for SAR → EGP. Same-currency conversion returns the original amount.

For a report using the latest-rate policy:

1. Filter daily metrics by the requested date range in the database.
2. Aggregate Spend and Revenue by source currency/account; retain raw count totals.
3. Load the required rates once from one published snapshot.
4. Convert monetary subtotals to `Client.Currency` and then add them together.
5. Recalculate `CPA = totalSpend / totalConversions`, `CPC = totalSpend / totalClicks`, `CPM = totalSpend / totalImpressions * 1000`, `ROAS = totalRevenue / totalSpend`, and `CTR = totalClicks / totalImpressions * 100`, with the application's explicit zero-denominator policy. Do not average platform ratios or convert counts/percentages as money.
6. Return reporting currency, snapshot ID, rate effective timestamp, and freshness status with the report. Round for display, not repeatedly during aggregation.

If historical daily conversion is chosen instead, convert each day's monetary totals with that day's defined snapshot before summing. Aggregating a whole period first and applying one rate would implement a different reporting policy.

## 7. Failure and operating behavior

- When refresh fails, keep existing rates and expose their effective date/freshness. Define a configurable maximum usable age; when exceeded, return converted totals as unavailable rather than silently presenting them as current.
- If no usable snapshot or a required currency is missing, return a clear conversion-unavailable result for mixed-currency totals. Never substitute rate 0 or 1. Native-currency views can still work.
- Reject incomplete, nonpositive, malformed, or older-than-current rate sets. Store failure categories/status codes without logging API keys, credential-bearing URLs, raw provider bodies, or headers containing secrets.
- A hosted worker runs only while its host is running. A daily refresh during web-app downtime requires an always-running worker or external scheduler. On restart, fetch the latest snapshot when due; do not issue one request for every missed day. Historical backfill is a separate feature.
